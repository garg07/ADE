⚡ Databricks & Delta Lake
Q1 What is Delta Lake and how does it differ from Parquet?
Basic
Delta Lake is a storage layer that sits on top of cloud storage (ADLS/S3) and brings ACID transactions to data lakes. Key differences: • Parquet: Just a columnar file format. No transactions, no update/delete support, no schema enforcement. • Delta Lake: Adds a transaction log (_delta_log), ACID transactions, DML support (UPDATE/DELETE/MERGE), schema enforcement/evolution, time travel (RESTORE), Z-ordering for data skipping. Delta files ARE Parquet under the hood — Delta adds the transaction log on top.
Q2 Explain Z-ordering in Delta Lake. When should you use it?
Mid
Z-ordering co-locates related data in the same set of files to speed up queries that filter on those columns. When to use: High-cardinality columns frequently used in WHERE clauses (e.g., customer_id, transaction_date). Avoid on low-cardinality columns like status flags.
OPTIMIZE table_name ZORDER BY (customer_id, event_date)
Important: Z-ordering only helps AFTER OPTIMIZE is run. Combine with VACUUM to clean up old files. It does not replace partitioning — use both together.
Q3 How does MERGE (upsert) work in Delta Lake? Write an example.
Mid
MERGE allows you to insert, update, or delete rows in a Delta table based on a match condition — similar to SQL MERGE.
MERGE INTO target_table AS t USING source_df AS s ON t.id = s.id WHEN MATCHED AND s.is_deleted = true THEN DELETE WHEN MATCHED THEN UPDATE SET t.value = s.value, t.updated_at = s.updated_at WHEN NOT MATCHED THEN INSERT (id, value, updated_at) VALUES (s.id, s.value, s.updated_at)
Common use case: CDC pipelines — merge incoming changes from Kafka/Event Hubs into the Silver/Gold Delta table. Efficient because Delta's transaction log handles it atomically.
Q4 What is Unity Catalog? How does it improve over legacy Hive Metastore?
Advanced🔥 Trending
Unity Catalog is Databricks' unified governance layer for data and AI, using a 3-level namespace: catalog.schema.table. Advantages over Hive Metastore: • Centralized governance across all workspaces (not per-workspace) • Fine-grained access control: row-level, column-level security • Built-in data lineage (table → column level) • Auditing via system tables • AI/ML asset governance (models, features, volumes) • Works across clouds (multi-cloud governance) Key concepts: Metastore (top level, per region) → Catalog → Schema → Table/View/Volume
🔥 Asked frequently in 2025–26 interviews for senior roles. Know how to set up a metastore and assign grants.
Q5 What are Delta Live Tables (DLT)? How do they simplify ETL?
Advanced🔥 Trending
Delta Live Tables (DLT) is a declarative ETL framework in Databricks. You declare what the pipeline should produce, and Databricks handles orchestration, dependency resolution, retries, and monitoring. Key features: • Declarative: define tables with @dlt.table decorator • Built-in data quality with EXPECT clauses (Expectations) • Automatic lineage tracking • Simplifies streaming + batch in one framework
import dlt @dlt.table def silver_orders(): return dlt.read("bronze_orders").filter("status != 'CANCELLED'")
Expectations example:
@dlt.expect("valid_amount", "amount > 0") @dlt.expect_or_drop("valid_id", "id IS NOT NULL")
Q6 How do you implement Structured Streaming in Databricks? Explain checkpointing and watermarking.
Advanced
Structured Streaming processes data as an unbounded table. New data is appended to the input table; queries run continuously. Checkpointing: Tracks the progress of a streaming query (offsets consumed). Enables fault recovery — stream resumes from where it left off on failure. Watermarking: Tells Spark how late data can arrive and still be processed. Prevents unbounded state growth.
df.withWatermark("event_time", "10 minutes") .groupBy(window("event_time", "5 minutes"), "user_id") .count() .writeStream .format("delta") .option("checkpointLocation", "/mnt/checkpoints/stream1") .outputMode("append") .start("/mnt/delta/agg_output")
🔄 Azure Data Factory
Q7 What are the 4 types of triggers in ADF? When do you use each?
Basic
1. Schedule Trigger: Runs at fixed time intervals (e.g., daily at 2 AM). Best for: batch jobs with predictable schedules. 2. Tumbling Window Trigger: Fixed non-overlapping time windows. Supports backfilling historical data. Best for: time-partitioned loads where each window is independent. 3. Event-based Trigger (Storage Event): Fires when files arrive in Blob/ADLS. Best for: file-arrival-driven pipelines. 4. Custom Event Trigger: Fires on custom events in Azure Event Grid. Best for: event-driven architectures across services.
Q8 What are Integration Runtimes in ADF? What's the difference between Azure IR and Self-hosted IR?
Mid
Integration Runtime (IR) is the compute infrastructure used by ADF to run data movement and transformation activities. Azure IR: Managed by Microsoft. Used for cloud-to-cloud data movement (Azure services). Auto-scales. No maintenance needed. Self-hosted IR: Installed on your on-premises server or private VM. Required when: source/destination is on-prem (SQL Server, Oracle), or inside a private VNet without public endpoint. Azure-SSIS IR: Runs legacy SSIS packages in the cloud. Used when migrating on-prem SSIS workloads to Azure.
🔥 Interviewers love asking: "How would you connect ADF to an on-prem Oracle database?" → Self-hosted IR + Oracle linked service.
Q9 How do you implement CI/CD for ADF pipelines?
Advanced🔥 Trending
ADF CI/CD flow using Azure DevOps: 1. Git Integration: Connect ADF to Azure Repos (collaboration branch = main/develop) 2. ARM Export: ADF publishes changes as ARM templates to adf_publish branch 3. Build Pipeline: Trigger on merge to adf_publish → validate ARM templates 4. Release Pipeline: Deploy ARM templates to DEV → QA → PROD using Azure Resource Manager task 5. Parameter Files: Use environment-specific parameter files for linked service URLs, storage accounts 6. Pre/Post deployment: Stop triggers before deploy, start after Best practice: Never manually edit PROD ADF. All changes flow through Git → PR → pipeline only.
Q10 How do you handle failed activities and retries in ADF?
Mid
Error handling strategies in ADF: 1. Retry policy: Set retry count + interval on each activity for transient failures 2. Failure path: Add an "On Failure" dependency edge to a notification or logging activity 3. If Condition / Switch: Branching logic based on activity output 4. Error logging: Write error details to Azure SQL or Blob using a Copy Activity on the failure path 5. Alerts: Configure Azure Monitor alerts on pipeline failures → trigger Logic App / email 6. Dead letter queue: For streaming pipelines, send failed messages to a dead-letter Event Hub
🐍 PySpark & Performance
Q11 What is the difference between repartition() and coalesce()?
Basic
repartition(n): Full shuffle — redistributes data evenly across n partitions. Use to INCREASE partitions or create even distribution. coalesce(n): Minimizes shuffle — merges partitions without full shuffle. Use to DECREASE partitions (e.g., before writing to fewer output files). More efficient than repartition for reduction.
# Increase partitions (repartition for parallelism) df.repartition(200) # Decrease partitions before write (avoids shuffle) df.coalesce(10).write.format("delta").save(path)
Rule of thumb: repartition to increase, coalesce to decrease.
Q12 How do you handle data skew in PySpark? Explain the salting technique.
Advanced
Data skew occurs when certain partition keys have disproportionately more data, causing one executor to process most of the work. Salting technique: Add a random salt to the join key to distribute skewed keys across multiple partitions.
# Add salt to large (skewed) table salt_factor = 10 df_large = df_large.withColumn("salt", (rand() * salt_factor).cast("int")) df_large = df_large.withColumn("salted_key", concat(col("join_key"), lit("_"), col("salt"))) # Explode small table to match all salt values df_small = df_small.withColumn("salt", explode(array([lit(i) for i in range(salt_factor)]))) df_small = df_small.withColumn("salted_key", concat(col("join_key"), lit("_"), col("salt"))) result = df_large.join(df_small, "salted_key")
Other approaches: Broadcast join (if one table is small), AQE (Adaptive Query Execution) in Spark 3.x auto-handles skew.
Q13 What is Adaptive Query Execution (AQE)? What problems does it solve?
Advanced
AQE (Spark 3.0+) is an optimization framework that dynamically adjusts query plans at runtime based on actual statistics. Problems it solves: 1. Skew joins: Automatically splits skewed partitions into smaller sub-partitions 2. Coalescing shuffle partitions: Reduces the number of post-shuffle partitions dynamically (no need to manually set spark.sql.shuffle.partitions) 3. Switching join strategies: Converts sort-merge join to broadcast join when one side is found to be small at runtime
spark.conf.set("spark.sql.adaptive.enabled", "true") spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
AQE is enabled by default in Databricks Runtime 7.3+. It's a game-changer for production pipelines.
Q14 When would you use a broadcast join vs a sort-merge join?
Mid
Broadcast Join: Copies the smaller DataFrame to all executors. No shuffle needed. Very fast. Use when: one side of the join is small (< broadcast threshold, default 10MB).
from pyspark.sql.functions import broadcast result = large_df.join(broadcast(small_df), "key")
Sort-Merge Join (default): Both DataFrames are sorted and merged. Involves shuffle. Efficient for large-large joins. Use when: both tables are large and can't fit in memory. Shuffle Hash Join: Builds a hash table from one side. Faster than sort-merge for medium datasets. Enabled via hint or config.
Q15 Explain the difference between cache() and persist() in PySpark.
Mid
cache() = shortcut for persist(StorageLevel.MEMORY_AND_DISK). Stores data in memory; spills to disk if memory is full. persist() = explicit storage level control:
from pyspark import StorageLevel df.persist(StorageLevel.MEMORY_ONLY) # Memory only, recompute if evicted df.persist(StorageLevel.MEMORY_AND_DISK) # Default (same as cache) df.persist(StorageLevel.DISK_ONLY) # Disk only df.persist(StorageLevel.MEMORY_AND_DISK_SER) # Serialized (less memory, more CPU)
When to use: Cache DataFrames that are reused multiple times in a job (e.g., a filtered base table joined multiple times). Always unpersist() after use.
🗄️ SQL & Data Modeling
Q16 Write a SQL query to find the 2nd highest salary per department.
Mid
-- Using DENSE_RANK (handles ties correctly) WITH ranked AS ( SELECT employee_id, department_id, salary, DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk FROM employees ) SELECT employee_id, department_id, salary FROM ranked WHERE rnk = 2;
Why DENSE_RANK over ROW_NUMBER? DENSE_RANK handles ties — if two employees share the highest salary, DENSE_RANK gives them both rank 1 and the next gets rank 2. ROW_NUMBER would skip rank 2 in that case.
Q17 Explain SCD Type 2. How do you implement it in ADF + Databricks?
Advanced
SCD Type 2 tracks historical changes by adding new rows for each change, with effective_start_date, effective_end_date, and is_current flag. Implementation in Databricks using Delta MERGE:
-- Step 1: Mark existing active records as expired where data changed MERGE INTO dim_customer AS target USING ( SELECT id, name, city, current_date() as eff_start FROM staging_customer ) AS source ON target.id = source.id AND target.is_current = true WHEN MATCHED AND (target.name != source.name OR target.city != source.city) THEN UPDATE SET target.is_current = false, target.eff_end_date = current_date() WHEN NOT MATCHED THEN INSERT (id, name, city, eff_start_date, eff_end_date, is_current) VALUES (source.id, source.name, source.city, source.eff_start, '9999-12-31', true) -- Step 2: Insert new version for changed records INSERT INTO dim_customer SELECT id, name, city, current_date(), '9999-12-31', true FROM staging_customer s WHERE EXISTS (SELECT 1 FROM dim_customer d WHERE d.id = s.id AND d.is_current = false AND d.eff_end_date = current_date())
Q18 Write a query to calculate a 7-day rolling average of daily sales.
Advanced
SELECT sale_date, product_id, daily_revenue, AVG(daily_revenue) OVER ( PARTITION BY product_id ORDER BY sale_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW ) AS rolling_7d_avg FROM daily_sales ORDER BY product_id, sale_date;
Key concept: "ROWS BETWEEN 6 PRECEDING AND CURRENT ROW" = current row + 6 prior rows = 7 rows total. Use RANGE BETWEEN for date-based windows (handles gaps in dates).
☁️ Azure Architecture & Services
Q19 Explain the Medallion Architecture (Bronze/Silver/Gold). What goes in each layer?
Mid
Medallion Architecture is a layered data organization pattern in a Lakehouse. Bronze (Raw): Raw ingested data, exactly as received from source. No transformations. Append-only. Preserves source history. Good for data replay/reprocessing. Silver (Cleansed): Validated, deduplicated, type-cast, lightly transformed data. Joins across sources may happen here. Conformed to business rules. Gold (Business): Aggregated, business-ready datasets — KPIs, star schema models, ML feature sets. Consumed by BI tools, dashboards, data science. Benefits: Clear data lineage, incremental processing, easy to debug by re-running a single layer, audit compliance.
Q20 How do you handle data security in Azure Data Lake (ADLS Gen2)? Explain RBAC vs ACLs.
Advanced🔥 Trending
RBAC (Role-Based Access Control): Coarse-grained. Applied at storage account or container level using Azure AD roles (Storage Blob Data Reader, Contributor, Owner). ACLs (Access Control Lists): Fine-grained. Applied at file/folder level using POSIX-like permissions (read/write/execute). Only available in ADLS Gen2 (hierarchical namespace enabled). Best practice: • Use RBAC to grant broad access to service principals / Databricks clusters • Use ACLs to restrict specific folders to specific teams • Use Managed Identity for Databricks → ADLS auth (no credentials in code) • Encrypt data at rest with Azure-managed keys or Customer-managed keys (CMK) via Key Vault • Enable Private Endpoints to prevent data exfiltration over public internet
Q21 When would you choose Azure Synapse Analytics over Databricks?
Advanced
Choose Synapse when: • Primary workload is T-SQL querying / traditional DW (dedicated SQL pools) • Team is SQL-heavy, less Python/Scala expertise • Need tight Power BI integration with a familiar SSAS-like model • Serverless SQL for ad-hoc exploration over ADLS without a cluster • Organization has heavy Microsoft licensing / cost consolidation preference Choose Databricks when: • Complex data transformations with PySpark / Scala • ML/AI workloads alongside data engineering • Advanced streaming with Structured Streaming • Need Unity Catalog governance • High-performance Delta Lake operations at scale Reality: Many enterprises use BOTH — ADF/Synapse for orchestration & DW layer, Databricks for transformation & ML.
🐍 Python for Data Engineering
Q22 How would you implement an idempotent data pipeline in Python?
Mid
Idempotent = running the pipeline multiple times produces the same result (no duplicates, no data loss). Strategies: 1. Overwrite partitions: Use INSERT OVERWRITE or Delta's replaceWhere to overwrite specific partitions 2. MERGE/UPSERT: Use Delta MERGE on natural key — inserts new, updates existing 3. Watermark tracking: Track max processed timestamp, only process newer records 4. Hashing: Generate a row hash, skip rows that already exist in target
def run_pipeline(execution_date): # Load only data for the given date partition df = spark.read.format("parquet").load(source_path) \ .filter(f"date = '{execution_date}'") # Overwrite exactly that partition (idempotent) df.write.format("delta") \ .mode("overwrite") \ .option("replaceWhere", f"date = '{execution_date}'") \ .save(target_path)
Q23 Explain generators vs list comprehensions in Python. When do you prefer each for data engineering?
Advanced
List comprehension: Creates entire list in memory at once. Fast for small-medium data.
data = [transform(row) for row in df.collect()] # All in memory
Generator: Produces values lazily, one at a time. Memory-efficient for large data.
def process_rows(df): for row in df.toLocalIterator(): # Streams rows one at a time yield transform(row) # Use in pipeline: for processed_row in process_rows(large_df): write_to_sink(processed_row)
In data engineering: Prefer generators when processing large result sets locally (e.g., iterating API responses, file chunks). For Spark transformations, use DataFrame API — generators/lists are for driver-side processing only.

S1 🔥 SCENARIO: Your ADF pipeline runs daily, but today it processed duplicate records. How do you investigate and fix it?
Scenario🔥 Hot
Investigation steps: 1. Check ADF Monitor: Look at pipeline run history — did it run more than once? Check trigger history for double-fires. 2. Check Delta Table History:
DESCRIBE HISTORY my_table LIMIT 10; -- Look for multiple WRITE/MERGE operations on same date
3. Check Source: Did source data itself contain duplicates? Use COUNT vs COUNT(DISTINCT key). 4. Check Pipeline Logic: Was it an append-only load without deduplication? Fix options: • Immediate: RESTORE to previous snapshot using Delta Time Travel: RESTORE TABLE my_table TO VERSION AS OF 5 • Prevention: Switch from append to MERGE (upsert) on natural key • Prevention: Add idempotency — use replaceWhere for date partitions • Prevention: Add a pipeline run log table to prevent double-execution on same date
S2 🔥 SCENARIO: A PySpark job that used to run in 20 mins now takes 3 hours. What's your debugging approach?
Scenario🔥 Hot
Step 1 — Check Spark UI: • Identify which stage is slow • Look for tasks with vastly different durations (data skew sign) • Check GC time, spill to disk metrics Step 2 — Common culprits: • Data growth: Input size increased → check partition count (aim for ~128MB–256MB per partition) • Skew: One executor processing 90% of data → add salting or enable AQE • Bad join: Sort-merge join on skewed key → add broadcast hint if one side is small • Missing cache: Recomputing the same DataFrame multiple times • Cluster change: Cluster downsized or moved to spot instances Step 3 — Fixes:
spark.conf.set("spark.sql.adaptive.enabled", "true") spark.conf.set("spark.sql.shuffle.partitions", "400") # Increase for large data df.cache() # Cache reused DataFrames df.join(broadcast(small_dim), "key") # Broadcast small dimensions

Architecture: Ingestion: IoT devices → Azure IoT Hub → Azure Event Hubs (buffer + partitioning) Processing: Databricks Structured Streaming reads from Event Hubs
df = spark.readStream \ .format("eventhubs") \ .options(**ehConf) \ .load() # Parse JSON payload parsed = df.select(from_json(col("body").cast("string"), schema).alias("data")) # Apply anomaly detection logic (e.g., threshold or ML model) anomalies = parsed.filter(col("data.temperature") > 90)
Alerting: anomalies written to Event Hubs → Logic App → email/SMS/Teams notification Storage: • Raw → ADLS Bronze (append) • Parsed + enriched → Delta Silver (MERGE with dedup) • Aggregated 1-min stats → Delta Gold (for dashboard) Monitoring: Azure Monitor + Databricks Ganglia metrics for stream lag

S5 SCENARIO: You need to process 500 million records daily with SLA of 2 hours. How do you architect this?
ScenarioAdvanced
Key design principles for this scale: 1. Partitioning strategy: Partition source data by date + region. Process each partition in parallel. 2. Cluster sizing: Auto-scaling Databricks cluster — 10–30 workers (Standard_DS4_v2 or similar), enable spot instances for cost. 3. Format: Delta Lake with appropriate partitioning. Avoid small files (use OPTIMIZE after write). 4. Processing pattern:
spark.conf.set("spark.sql.shuffle.partitions", "800") spark.conf.set("spark.sql.adaptive.enabled", "true") # Read with predicate pushdown df = spark.read.format("delta").load(source) \ .filter(f"date = '{today}'") # Process in stages to enable caching of shared intermediate DFs base = df.join(broadcast(dim_product), "product_id").cache() # Write with partition optimization base.write.format("delta").mode("overwrite") \ .option("replaceWhere", f"date = '{today}'") \ .save(output_path)
5. Monitoring: Set up Databricks Jobs with email alerts. Track stage completion times.
S6 SCENARIO: How would you implement data quality checks in your pipeline?
ScenarioMid
Multi-layer data quality strategy: Layer 1 — Schema validation (at ingestion): • Delta Lake schema enforcement: rejects records with wrong types • ADF Mapping Data Flows: define type casting and null handling Layer 2 — Rule-based checks (in Databricks):
def check_quality(df, table_name): checks = { "null_check": df.filter(col("id").isNull()).count(), "negative_amount": df.filter(col("amount") < 0).count(), "future_date": df.filter(col("txn_date") > current_date()).count(), } failed = {k: v for k, v in checks.items() if v > 0} if failed: raise Exception(f"DQ Failed for {table_name}: {failed}")
Layer 3 — Statistical checks: • Row count vs previous day (alert if > ±20% deviation) • Null rate per column (alert if crosses threshold) Layer 4 — DLT Expectations (if using DLT):
@dlt.expect_or_drop("no_null_id", "id IS NOT NULL") @dlt.expect("positive_amount", "amount > 0")
Logging: Write DQ results to a separate Delta table for auditing and dashboards.
